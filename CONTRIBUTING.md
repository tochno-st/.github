## Нашли баг или хотите предложить улучшение?

- Проверьте, не создан ли похожий issue.
- Создайте новый Issue (используйте готовые шаблоны, если они есть).

## Политика работы с issues

### 1. Общие положения

Назначьте себя исполнителем Issue, а если нет прав - попросите мейнтейнера или лида.

Перед созданием PR сделайте rebase на актуальную main-ветку и убедитесь, что история соответствует правилам раздела [Единица работы (Unit of Work)](#единица-работы-unit-of-work-и-история-коммитов), и только затем открывайте PR.

Руководствуйтесь следующим:

- **Атомарность** - каждый коммит делает только одно дело. Заметили участок для рефакторинга - вынесите его в отдельный
  коммит.
- **Работоспособность** - каждый финальный коммит должен быть рабочим: без сломанного приложения или падающих тестов.

В описании PR чётко объясните суть изменений и приложите ссылки на связанные задачи и обсуждения - это поможет быстрее войти в контекст.

При необходимости добавьте чек-лист выполненных пунктов: тесты пройдены, документация обновлена, код покрыт тестами и т.д.

Относитесь к ревью ответственно: учитывайте все замечания и не оставляйте нерешённых вопросов.

Для критичных частей системы (БД, инфраструктура) обязательно проведите дополнительные тесты или попросите ревью у коллег.

Если работа долгая - создайте черновой (draft) PR, чтобы команда видела прогресс.

### 2. Закрытие Issues

#### 2.1 Право на закрытие

Issue закрывает не автор автоматически, а лицо, принимающее результат согласно определению готовности. Закрытие
выполняют:

- **Автор Issue** - если он является заказчиком или инициатором задачи.
- **Ответственное лицо (Product Owner, Tech Lead, QA)** - если инициатор и исполнитель различаются.
- **Мейнтейнер** - для внешних Issue.

#### 2.2 Основания для закрытия

Issue может быть закрыт после:

- успешного прохождения CI-проверок;
- мердж в main-ветку;
- решения мейнтейнера (не планируется к реализации, не оформлен должным образом, обсуждение завершено и т.п.).

#### 2.3 Модель ответственных

| Тип Issue   | Кто закрывает                                   |
|-------------|-------------------------------------------------|
| Feature     | Автор (владелец требований) или Product Owner   |
| Bug         | Тот, кто подтвердил фикс и проверил исправление |
| Tech debt   | Tech Lead или владелец компонента               |
| Refactoring | Reviewer, подтвердивший отсутствие регрессий    |

### 3. Code Review и Merge-политика

#### 3.1 Общие требования

Pull Request допускается к мерджу при выполнении условий:

- все CI-проверки зелёные;
- нет открытых блокирующих комментариев.

Одобрять изменения могут:

- мейнтейнеры и члены core team;
- владельцы соответствующего компонента;
- Tech Lead - для критически важных областей.

#### 3.2 Merge в main-ветку

Approval лида обязателен для:

- изменений бизнес-логики;
- архитектурных изменений;
- изменений интерфейсов (API);
- вопросов безопасности.

Approval не требуется для:

- багфиксов без изменения контракта;
- рефакторинга без изменения поведения;
- обновления документации.

Рекомендуется настроить **branch protection rules** для main-ветки.

#### 3.3 Merge в production

Merge в production - техническая операция, выполняется только после полного ревью релизного PR.

#### 3.4 Удаление веток после merge

После мерджа PR в main ветка удаляется. Ответственность за удаление лежит на авторе PR (или на том, кто выполнил мердж).

Для этого рекомендуется включить на GitHub настройку «Automatically delete head branches» - тогда ветка удаляется автоматически при мердже, и не нужно помнить об этом вручную. Правило ниже остаётся fallback-ом для случаев, когда автоудаление недоступно или не сработало.

- Ветки с открытым PR (в том числе Draft) не удаляются до мерджа или закрытия PR.
- Ветки без открытого PR и без активности (stale) подлежат удалению; при сомнениях уточните у автора или мейнтейнера.
- Долгоживущие (например, релизные) ветки не удаляются.
- Если ветка нужна после мерджа (хотфикс, доделки) - заранее предупредите об этом в PR и удалите её, как только надобность отпала.
- После удаления remote-ветки синхронизируйте локальный репозиторий: `git fetch --prune`, затем `git branch -d <имя>`.

### 4. Наименование веток

Формат: `<тип>/<краткое-описание>`.

Тип ветки соответствует префиксу коммита из секции [Коммит-месседжи](#коммит-месседжи-префиксы-и-правила). Описание на английском, kebab-case, без лишних слов.

| Тип        | Пример                          |
|------------|---------------------------------|
| `feat`     | `feat/add-court-filter`         |
| `fix`      | `fix/null-pointer-in-parser`    |
| `docs`     | `docs/update-readme`            |
| `refactor` | `refactor/extract-http-client`  |
| `chore`    | `chore/update-dependencies`     |
| `test`     | `test/add-case-fixtures`        |
| `build`    | `build/pin-httpx-version`       |
| `ci`       | `ci/add-flake8-check`           |

### 5. Политика Force Push

Force push - инструмент для приведения истории в порядок, а не право по умолчанию. Применяйте его
осознанно и уважительно по отношению к чужой работе.

#### 5.1 Индивидуальные ветки

Индивидуальная ветка - ветка одного автора без открытого PR (включая Draft).

В них force push разрешён свободно в любой момент: rebase, сквош и перестановка коммитов - для
достижения чистоты истории по разделам «Коммит-месседжи» и «Единица работы (Unit of Work)».

#### 5.2 Командные ветки

Командные - долгоживущие (main, release) и общие ветки, где вклад вносят несколько человек.

- На main и release force push допускается в экстренных случаях, его может делать только лид.
- В общей фиче-ветке force push разрешён только автору PR и только в фазе «после ревью, готовность
  к merge»: получен approval, нет блокирующих комментариев, CI зелёный. До завершения ревью
  переписывание истории не разрешается: замечания ревьюеров привязаны к конкретным коммитам.

В фазе «после ревью» force push используется только для чистки истории:

- rebase на актуальный main;
- сквош коммитов с правками по ревью в исходный;
- наведение порядка под единицу работы (UOW).

Код при этом не изменяется (в т.ч. не решаются конфликты rebase), поэтому approval остаётся
валидным и повторное ревью не требуется. Если rebase требует правок кода - верните PR в ревью.

#### 5.3 Практика

- Предпочтите `git push --force-with-lease` (или `--force-if-includes`) вместо `--force`: последний
  может незаметно затереть изменения, появившиеся на сервере после последнего fetch.
- Перед force push в общей ветке предупредите команду (PR/чат), если кто-то ещё в ней работает.
- После чужого force push: `git fetch --prune`, затем при необходимости `git reset --hard origin/<ветка>`;
  незакоммиченные правки сохраните заранее.

## Работа со связанными PR (stacked PR)

Stacked (связанные) PR - несколько PR, которые зависят друг от друга. Верхний PR невозможно внедрить до мерджа нижнего. Это могут быть независимые фичи, объединять их в один PR нельзя (см. [Единица работы (Unit of Work)](#единица-работы-unit-of-work-и-история-коммитов)).

- Stacked PR разрешены, но с ограничениями: не более 3 PR в одном стеке. При большем размере пересмотрите декомпозицию фич.

### База PR

- База верхнего PR - ветка нижнего PR (не main).
- Нижний (нижние) PR - база стека; верхние строятся на них.
- В описании верхнего PR указывается явная строка `stack: #N` - ссылка на базовый PR.

### Ревью

- Ревью идет снизу вверх, как и мердж.
- Верхний PR считается готовым к ревью только когда его база готова: base PR получил approval, CI зелёный, нет блокирующих комментариев.

### Мердж

- Мерджить строго снизу вверх, без исключений.
- После мерджа base PR верхний PR перебазируется на актуальный main и его база становится стабильной. Порядок действий: мердж base - rebase верхнего - новый цикл ревью.

### Взаимодействие с политикой force push

- База стека используется чужими верхними PR, поэтому считается командной веткой: применяется правило [5.2](#52-командные-ветки) (force push только после ревью, в фазе готовности к merge), действует только для базы стека.
- После force push в базе автор базы предупреждает владельцев верхних PR; каждый владелец сам делает rebase своей ветки на новую базу.
- GitHub не умеет перебазировать верхние PR автоматически при изменении базы.
- Держите верхние PR (в т.ч. Draft) открытыми и синхронизированными с базой - история верхнего PR не должна отставать от базы.

### CI

- CI верхних PR гоняется на текущей базе стека (если база ещё не в main), в описании PR явно помечается, что база ещё не замержена.
- После мерджа базы CI перепрогоняется на актуальной main-базе.

## Коммит-месседжи: префиксы и правила

### Префиксы

| Тип        | Описание                                     |
|------------|----------------------------------------------|
| `feat`     | новое функциональное изменение               |
| `fix`      | исправление багов                            |
| `docs`     | документация                                 |
| `style`    | форматирование, не влияющее на логику        |
| `chore`    | прочее, не влияющее на бизнес-логику и тесты |
| `refactor` | рефакторинг без изменения логики             |
| `perf`     | оптимизация производительности               |
| `test`     | добавление тестов                            |
| `build`    | изменения в зависимостях и сборке            |
| `ci`       | изменения в CI/CD                            |
| `revert`   | откат предыдущих коммитов                    |

> **Правило**: один коммит - один префикс и одна единица работы (UOW). Разные типы коммитов не объединяются в один
> (см. [Единица работы](#единица-работы-unit-of-work-и-история-коммитов)).

### Формат

```
<префикс>: <сообщение>
```

Префикс в нижнем регистре, после двоеточия пробел. Заголовок сообщения желательно не больше 50 символов, без точки в конце.

Тело коммита (опционально) отделяется пустой строкой. `BREAKING CHANGE` также отделяется пустой строкой.

Примеры:

```
chore: .gitignore
```

```
fix: prevent racing of requests

Introduce a request id and a reference to latest request. Dismiss incoming
responses other than from latest request.
```

```
feat: allow provided config object to extend other configs

BREAKING CHANGE: extends key in config file is now used for extending other
config files
```

См. [дополнительные примеры](https://www.conventionalcommits.org/en/v1.0.0/#examples).

### Когда использовать BREAKING CHANGE

- Изменения, несовместимые с предыдущей версией.
- Изменения, радикально расширяющие функциональность.

> Перед выпуском major-версии предупредите команду.

## WIP и временные (temp) коммиты

### WIP-коммиты

WIP - рабочий статус коммита, когда фича ещё не завершена. Допускается в личных ветках и в Draft PR. Используется, чтобы фиксировать промежуточный прогресс и позволить команде видеть работу на ранней стадии.

Формат:

```
<разрешённый-тип>: WIP
```

- Тип - один из разрешённых (`feat`, `docs`, `refactor` и т.д.), WIP заглавными, описания не требуется.
- Допустимо несколько одинаковых коммитов `WIP` без описания - описание будет добавлено при слиянии WIP в итоговый рабочий коммит.
- WIP не является самостоятельной единицей работы (UOW).

### Временные (temp) коммиты

Temp - временный/отладочный коммит (отладочный код, логи, эксперименты). Допускается в тех же местах, что и WIP: в личных ветках и Draft PR.

Формат:

```
<тип>: temp <описание>
```

Например: `fix: temp debug logging`.

### Финализация

Временные и WIP-коммиты не должны попадать в командную фазу. Обязательно переработайте историю перед вводом в командную фазу (см. 5.2): сквошьте WIP/temp в чистовые коммиты, добавьте осмысленные описания. Чистая история - залог читаемости по UOW.

## Единица работы (Unit of Work) и история коммитов

Единица работы (UOW) - логически завершённый кусок работы, который автор хочет видеть в истории отдельным коммитом.
Чистая история - это когда один раз прочитав конвенцию команды, вы легко читаете фичи по истории.

### Что считать UOW

- Разные типы коммитов (`chore`, `docs`, `refactor`, `feat` и т.д.) - это всегда разные UOW. Такие коммиты не сквошат.
- Одинаковый тип не является поводом для сквоша: три коммита `chore` могут быть тремя разными задачами.
- Мелкая категоризация (например, считать ли `style` частным случаем `chore`) остаётся на усмотрение автора. Недопустимо называть `refactor` словом `chore` или, тем более, `feat`.
- Коммиты с правками по ревью (исходная работа и её исправления) допустимо объединять в один.

### Что не стоит сквошить

Не сквошьте в фичу крупный служебный/технический коммит (например, прогон хуков, обновление зависимостей, новая
документация): иначе фича растворяется в «горе технического мусора» и её невозможно разобрать. Работа сделана, но история становится грязной с точки зрения логики.

### Порядок коммитов

Технические и служебные коммиты размещайте сверху истории фичи, не закапывая их в середину.

### Число коммитов в PR

- Для обычной задачи достаточно 1-3 коммитов.
- Крупную фичу бьём на логические шаги так, чтобы каждый коммит оставался рабочим (без сломанного приложения и падающих тестов). Однако, тесты допустимо делать отдельным коммитом, если их объем большой и это превращается в отдельный UOW.
- Если разбить на рабочие коммиты не получается - создайте Draft PR с нерабочими коммитами, обсудите контекст с командой, а затем объедините их в один рабочий коммит.

### Merge-стратегия и история

Мы придерживаемся стратегии merge-коммитов. При этом сам merge-коммит является «зонтиком» над фичей (границей UOW), поэтому атомарные коммиты внутри сквошить нет смысла.

## Conventions и best practices

- Строго следуйте типизации, принятой в проекте.
- Соблюдайте единые архитектурные подходы кодовой базы.
- Поддерживайте консистентную структуру модулей и пакетов.
- Запускайте pre-commit.
- Перед созданием PR прогоняйте тесты.
